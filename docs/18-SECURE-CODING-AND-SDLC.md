# Secure Coding and Secure SDLC Standard

Status: **NORMATIVE**

## 1. Purpose

FinServ Agent Gateway is a security enforcement product. Secure coding is therefore a product requirement, not an implementation preference.

Every implementation and every contribution MUST satisfy this document. Code authored by a human, generated by an AI coding assistant, or produced by an autonomous coding agent is subject to the same controls. Generated code receives no trust advantage and no exemption from review or security gates.

## 2. Normative security references

The version-pinned registry in `security/standards-baseline.yaml` is authoritative for external security references. Baseline v0.1 requires engineering practices aligned to:

- NIST SP 800-218 SSDF v1.1;
- NIST Privacy Framework v1.0 for sensitive-data/privacy-risk design review;
- OWASP ASVS v5.0.0;
- OWASP Top 10:2025;
- OWASP API Security Top 10:2023;
- OWASP Top 10 for Agentic Applications 2026;
- OWASP GenAI LLM Top 10 2026 where LLM/GenAI components or callers are in scope;
- SLSA v1.2 for source/build supply-chain controls;
- CISA Secure by Design principles and current Product Security Bad Practices guidance.

A reference standard informs requirements; it does not create a blanket compliance claim. Conformance claims require an explicit crosswalk and evidence.

## 3. Coding principles

Implementation MUST follow these rules:

1. **Fail closed.** Parsing, authorization, policy, approval, persistence, or dependency uncertainty MUST NOT result in execution.
2. **Least privilege.** Code receives only the credentials, filesystem access, network access, database permissions, and action scope required for its function.
3. **Single enforcement path.** No helper, test hook, workflow pack, adapter, admin endpoint, or recovery path may bypass grant, policy, approval, idempotency, audit, and broker controls for governed actions.
4. **Untrusted input by default.** Network input, downstream responses, files, environment-derived data, tool output, model output, retrieved content, and inter-agent messages are untrusted until validated.
5. **No security through prompting.** Natural-language instructions, system prompts, model confidence, or agent assertions MUST NOT grant authority or replace deterministic validation.
6. **Minimize attack surface.** Prefer the standard library and small, auditable dependencies. Features that are not required are not exposed.
7. **Determinism at security boundaries.** Authorization, policy, approval binding, hashing, evidence verification, and replay must be deterministic.
8. **Explicit limits.** Inputs, outputs, time, concurrency, retries, and resource consumption must be bounded.
9. **No silent security degradation.** A missing control, unavailable verifier, or failed security scanner cannot be converted into PASS.
10. **Evidence over assertion.** Security gates produce machine-readable or durable evidence suitable for release review.

## 4. Go implementation requirements

The first implementation is expected to use Go. Before production code begins, the exact Go patch version and tool versions MUST be pinned in a reviewed implementation record.

### 4.1 Mandatory language/tool gates

At minimum, the implementation CI MUST run and pass:

- `gofmt` with zero diff;
- `go vet ./...`;
- `staticcheck ./...`;
- `go test ./...`;
- `go test -race ./...` for packages and integration paths that can run under the race detector;
- `govulncheck ./...`;
- `gosec ./...` or an explicitly approved equivalent Go SAST scanner;
- targeted Go fuzz tests for parsers and security-sensitive state machines.

Tool versions MUST be pinned. A scanner being unavailable is a failed gate, not a skip.

### 4.2 Prohibited or restricted constructs

The core gateway MUST NOT:

- use `unsafe` without a specific accepted ADR and security review;
- execute shell commands from request, tool, model, workflow-pack, policy, database, or downstream content;
- use `os/exec` in the governance kernel unless a later ADR defines a narrowly scoped, non-user-controlled use;
- load executable plugins or scripts from workflow packs;
- provide an `eval`, expression-language escape hatch, or dynamic code path in policy evaluation;
- disable TLS certificate verification;
- construct SQL by concatenating untrusted values;
- deserialize arbitrary polymorphic executable types;
- use panics as normal handling for malformed or hostile input.

### 4.3 Input and serialization safety

- JSON decoding is strict and duplicate-key rejecting.
- Request body sizes are bounded before decoding.
- Unknown normative fields are rejected.
- IDs and action names use documented canonical forms; security comparison is performed on normalized values only where normalization is explicitly defined.
- Hash inputs use frozen serialization rules; unordered maps must not accidentally become security hash material.
- File/archive paths are generated by trusted code and must reject traversal and absolute-path injection.

### 4.4 HTTP and network safety

Inbound servers MUST define explicit header, body, read, write, idle, and request-lifetime bounds appropriate to the endpoint.

Outbound adapters MUST:

- use server-side configured/registered destinations rather than caller-supplied arbitrary URLs;
- use explicit total deadlines;
- bound response bodies before parsing;
- use TLS verification for HTTPS;
- reject or tightly control redirects;
- avoid automatic retries for mutating requests whose outcome may be ambiguous;
- prevent caller-controlled SSRF through scheme, host, redirect, DNS, proxy, or alternate-IP tricks.

### 4.5 Database safety

- SQL parameters MUST be bound through the database driver; untrusted values are never interpolated into SQL text.
- Database roles use least privilege.
- Schema migrations are reviewed and versioned.
- Authorization decisions are not delegated to ad hoc SQL fragments assembled from request data.
- Transactions that bind approval consumption, action state, audit sequence, and dispatch state must preserve the invariants documented elsewhere in this baseline.

### 4.6 Cryptography and secrets

- Use Go standard-library cryptography or a separately reviewed, well-maintained cryptographic dependency.
- Do not implement custom cryptographic primitives.
- Security tokens and nonces use `crypto/rand`.
- Secret/token equality uses a constant-time comparison primitive where timing exposure is relevant.
- SHA-256 is used only for the integrity/binding purposes specified by the design, not as password hashing or as a confidentiality mechanism for low-entropy sensitive values.
- Low-entropy sensitive equality commitments use HMAC-SHA-256 (or a later explicitly approved keyed commitment) with a protected evidence key.
- Secrets are never committed, logged, placed in evidence bundles, or returned in diagnostic errors.
- Environment variables may bootstrap development credentials, but production secret-management integration is a deployment requirement.

### 4.7 Errors, logs and observability

- External errors do not leak stack traces, SQL, filesystem paths, credentials, policy internals, or raw downstream responses unless explicitly safe.
- Security decisions have stable machine-readable reason codes.
- Security-relevant failures are logged with correlation identifiers and redacted metadata.
- Logs are structured and must pass redaction tests.
- Authorization or approval failure cannot be downgraded to a warning followed by execution.

### 4.8 Concurrency and resource safety

- Security-sensitive mutable state must be race-free.
- Context cancellation and deadlines propagate to bounded operations.
- Goroutines must have defined ownership/lifetime; unbounded goroutine creation is prohibited.
- Queues, request bodies, response bodies, evidence exports, and concurrency are bounded.
- Mutating actions preserve at-most-once dispatch invariants under concurrency.

## 5. Dependency and supply-chain requirements

- Every direct dependency requires documented purpose and review.
- `go.mod` and `go.sum` are committed; dependency changes are isolated and reviewable.
- Release builds run `go mod verify` and dependency/vulnerability analysis.
- Known reachable vulnerabilities affecting the release are not silently accepted.
- Security exceptions require a documented owner, rationale, compensating control, expiry, and follow-up issue.
- Release artifacts include an SBOM in SPDX or CycloneDX format.
- Public/production release artifacts target at least SLSA v1.2 Build L2 provenance; higher levels are preferred when the build platform supports them.
- CI/CD third-party actions and reusable workflows must be version-pinned; mutable floating tags are not accepted for security-sensitive release jobs.
- Release artifacts and checksums are produced by the controlled build, not copied from an unverified developer workstation.

## 6. Source-control and review requirements

Once implementation begins:

- `main` is protected from direct feature commits;
- changes enter through pull requests;
- force-push to protected release history is disabled;
- required security/test checks must pass on the exact reviewed head revision;
- the final changed revision must be reviewed after the last code change;
- the authoring identity cannot satisfy its own mandatory human review;
- AI/agent-authored code MUST receive human review before merge;
- a coding agent MUST NOT approve its own changes, dismiss findings, alter branch protection, or waive required gates;
- changes to authentication, grants, policy, approval, broker dispatch, audit hashing, replay, cryptography, redaction, security schemas, or security baselines require explicit security-focused review.

## 7. Testing requirements

Security-sensitive components require positive, negative, boundary, concurrency, and adversarial tests. Coverage percentage alone is not evidence of security.

Mandatory techniques include:

- table-driven unit tests for authorization/policy/state machines;
- fuzzing of strict JSON/duplicate-key handling, policy parsing, identifiers, and evidence parsers;
- race testing;
- injection tests (SQL, header, path, URL/SSRF, structured-data confusion where applicable);
- authorization matrix tests;
- approval replay/substitution tests;
- redaction and secret-leak tests;
- timeout/ambiguous-outcome tests;
- malformed downstream response tests;
- tamper/replay tests.

## 8. Security waivers

A waiver MUST be explicit, reviewed, time-bounded, and linked to evidence. It MUST identify:

- the failed requirement/tool finding;
- affected versions/components;
- exploitability and impact;
- compensating control;
- owner;
- expiry date;
- remediation tracking reference.

Core governance invariants such as default deny, exact approval binding, no broker bypass, no silent ambiguous write retry, redaction of secrets, and zero-side-effect replay are **non-waivable** for a conforming release.

## 12. Sensitive-data implementation rule

Implementations of governed reads MUST enforce `21-SENSITIVE-DATA-ACCESS-GOVERNANCE.md`. Source-side projection, field/category filtering, purpose/destination checks, quantitative disclosure bounds, and redaction/tokenization are security controls and cannot be moved into optional logging/middleware.
